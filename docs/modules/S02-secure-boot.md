# Secure boot on PolarFire SoC: the chain of trust, and what we left alone

After this page you can explain how a signed boot works on this chip, name what has to be trusted from the start, say what the boot monitor checks and with which algorithm, and see exactly which steps would change the device itself. Those steps were **not** performed on this project's board, on purpose. What was done instead, and what it proves, is in the last two sections.

## Before you start

- **Level 3.** You should know the boot stages (E51 runs the boot monitor, which starts U-Boot and the real-time firmware).
- **Tools:** none to read it. To reproduce the offline demonstration, see module S03.

## The idea

A secure boot answers one question at every stage: *is the code I am about to run the code its owner signed?*

1. A small piece of code that cannot be modified (the **root of trust**) holds the owner's **public key**, or a hash of it.
2. It checks a **signature** on the next stage. The owner made the signature with a **private key** that is used only for signing and never stored in the device.
3. Only if the check passes does it start that stage. That stage then checks the one after it, and so on.
4. A **version number** that cannot go back stops an attacker from replaying an old, genuinely signed, vulnerable image (rollback).

The strength of the chain is the weakest link, and a check that is skipped or left disabled protects nothing. Module S03 shows each of these steps in a program you can run.

## How the PolarFire SoC does it

Taken from the boot monitor's source (the Hart Software Services, HSS) and Microchip's guide to authenticated boot.

**Link 1: the chip checks the boot monitor.** The guide calls this *factory secure boot*, boot mode 3, and says that mode "only supports authentication of the eNVM content": the chip verifies the boot monitor stored in its own non-volatile memory before the boot monitor runs.

**Link 2: the boot monitor checks the payload.** The payload is the file on the SD card that tells the boot monitor what to start on each core (U-Boot on three cores, the real-time firmware on the fourth). In the boot monitor's source, `HSS_Boot_Secure_CheckCodeSigning` does this:

1. Take the signature out of the image header, then set that field to zero.
2. Check an **ECDSA P-384** signature over the whole image (`bootImageLength` bytes), using **SHA-384**. The build can choose how: an open-source software implementation (libecc, the default) or the chip's crypto processor through the vendor library (module S01). The result is the same; the choice only decides where the arithmetic runs.
3. If it fails, the monitor prints "failure during signature verification..." and **spins forever**; the source even carries a note that it might raise a tamper flag. The guide says it plainly: "The PolarFire SoC RISC-V monitor and application processors will not be started if authentication fails."

The public key for this check is **compiled into the boot monitor** when the monitor is built (a build option, `CRYPTO_SIGNING`, with the path to a DER-format key). The option is on by default in the source's configuration, but it only means something once a key is supplied, and whether the boot monitor in this chip's flash was built with one is not known. The payload generator signs with the private key (`-p`) and can verify with the public key (`-d … -u`). The signature field in the image is the SHA-384 digest (48 bytes) followed by r and s of the signature (48 bytes each).

**Link 3 and beyond.** The guide describes a full chain on top of the boot monitor, with keys generated by a Yocto script. A common next link is U-Boot verifying a signed kernel image (a FIT image). This project has not tested that link.

## What would change the device

To turn Link 2 on for real, the guide's own steps are:

1. Build the boot monitor with signing enabled and your public key.
2. Program it into the chip's boot memory (eNVM), with the vendor's boot-mode programming tool (`make program BOOTMODE=3 …`).

Step 2 rewrites the boot flash of the chip and sets its boot mode. The guide says that if a stage's verification fails, "the device will not continue to boot." The pages used for this project do not say how to recover from a wrong key or image, and do not say which security settings of the device (user keys, passcodes, locks) can be undone once set. So the project's rule is to treat every one of them as possibly permanent.

### Rules this project follows on its board

| Rule | Why |
|---|---|
| Never program the eNVM, never use a boot-mode programming command | the boot monitor in the chip is the recovery path; without it an SD card can no longer boot the board |
| Never program user keys, passcodes or security locks | not documented as reversible |
| FPGA programming jobs contain the **fabric** and **sNVM** components only | the same jobs have been programmed many times, and the eNVM digest is identical before and after |
| Test a change to the SD card on a copy, keep the working image | the SD card is the one thing that can always be rewritten from a PC |

## What was done instead

Nothing here touches the board. All of it runs on a PC and is recorded as evidence:

- **A real signed payload.** The payload generator from the Yocto build signed this project's real boot payload with a throwaway key. The vendor tool verified it; flipping one bit, using an unsigned image, or using someone else's key made it fail.
- **A second implementation.** `verify_boot_image.py` was written from the boot monitor's source, not from the vendor tool. It found the signature field by itself and agreed with the vendor tool in all four cases.
- **A toy chain of trust.** `chain_demo.py` models root of trust, two stages and an application with the same algorithms, and plays six attacks against it: a flipped bit, a forged application, a forged stage naming the attacker's key, a rollback, and a swapped key.

What this proves is that the **format and the algorithm are understood and reproducible**. It does not prove anything about how the boot monitor already in this chip behaves when given a signed payload: it was not built with our key and the signed payload was never flashed.

## Trade-offs and going further

- **Verified boot above the boot monitor needs no device change.** Making U-Boot verify a signed kernel affects only the SD card. It is the right next step if you want a real, testable chain here, and it is recoverable by rewriting the card.
- **Authenticating the boot monitor is a one-way decision** in practice, and belongs on a board whose loss is acceptable.
- **A private key is the whole security.** The demonstration generates a key on disk to show the flow. A real key lives in a hardware security module and is never copied to a build machine.
- **Exercise:** in S03, make scenario 5 pass by changing the ROM's minimum version. What does that tell you about where the version counter must live?
